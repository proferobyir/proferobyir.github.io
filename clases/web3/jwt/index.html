Introduccion a las APIs REST y Endpoints

Una API REST (Representational State Transfer) es un conjunto de reglas y convenciones para construir servicios web que permiten la comunicacion entre sistemas de forma estandarizada. En el corazon de una API REST se encuentran los Endpoints, que son los puntos de acceso a los recursos del sistema.

En Express.js, la estructura formal de un endpoint sigue la firma sintactica:

Sintaxis Estructural en Express JavaScript 
app.METHOD('PATH', [MIDDLEWARES...], (req, res) => {
  // Funcion Manejadora
});

Los endpoints son la piedra angular de cualquier API REST, ya que permiten exponer funcionalidades y recursos del sistema a traves de una interfaz estandarizada y predecible.

Objetivos de Aprendizaje:
  • Comprender los principios fundamentales de REST y su aplicacion en APIs modernas
  • Identificar y utilizar correctamente los verbos HTTP en el diseno de endpoints
  • Implementar un sistema de autenticacion stateless con JWT
  • Proteger endpoints mediante middlewares de autorizacion
  • Integrar una base de datos MySQL con consultas preparadas

Principios Fundamentales de REST

REST (Representational State Transfer) es un estilo arquitectonico definido por Roy Fielding en su tesis doctoral en el año 2000. Para que una API sea considerada RESTful, debe cumplir con seis principios fundamentales:

1. Cliente-Servidor (Client-Server)

Separa claramente la interfaz de usuario (cliente) del almacenamiento de datos (servidor). Esto permite que ambos evolucionen de forma independiente y facilita la escalabilidad.

2. Sin Estado (Stateless)

Cada peticion del cliente al servidor debe contener toda la informacion necesaria para ser entendida y procesada. El servidor no almacena ningun estado de sesion entre peticiones. Cada solicitud es independiente y autocontenida.

3. Cacheable (Cacheability)

Las respuestas del servidor deben indicar explicitamente si pueden ser almacenadas en cache por el cliente o por intermediarios. Esto mejora el rendimiento al reducir la carga del servidor.

4. Interfaz Uniforme (Uniform Interface)

Define una interfaz estandar entre cliente y servidor que simplifica la arquitectura. Se compone de: identificacion de recursos, manipulacion mediante representaciones, mensajes autodescriptivos y hypermedia como motor del estado de la aplicacion (HATEOAS).

5. Sistema en Capas (Layered System)

La arquitectura puede organizarse en capas jerarquicas donde cada capa solo conoce a la inmediata inferior. Esto permite añadir proxies, balanceadores de carga y puertas de enlace sin afectar al cliente o al servidor final.

6. Codigo Bajo Demanda (Code on Demand - Opcional)

Los servidores pueden extender la funcionalidad del cliente enviando codigo ejecutable (como JavaScript o applets). Este es el unico principio opcional de REST.

Principios mas Relevantes para API Design:
  • Stateless: Es el principio que habilita la arquitectura con JWT que veremos mas adelante.
  • Interfaz Uniforme: Nos guia en el uso correcto de verbos HTTP y codigos de estado.
  • Client-Server: Permite que el frontend y backend se desarrollen de forma independiente.
Analogia REST como un Restaurante

Cliente (Comensal)

El comensal (cliente) llega al restaurante y hace un pedido. No necesita saber como se prepara la comida ni donde se almacenan los ingredientes.

Servidor (Cocina)

La cocina (servidor) recibe el pedido, prepara la comida y la entrega. No necesita saber quien es el comensal para cada pedido (stateless). Cada pedido es independiente.

Interfaz Uniforme (Menu)

El menu (interfaz uniforme) estandariza como se hacen los pedidos. Todos los comensales usan el mismo formato para ordenar: entrantes, plato principal, postre (verbos HTTP estandarizados).

Verbos HTTP y su Significado en REST

Los verbos HTTP (o metodos) son las acciones que el cliente puede realizar sobre los recursos del servidor. En una API RESTful, cada verbo tiene un significado especifico y debe usarse de acuerdo a las convenciones establecidas:

Verbo Color Operacion Idempotente? Seguro? Ejemplo de Uso
GET Verde Consultar / Leer Si Si Obtener lista de productos
POST Azul Crear / Insertar No No Crear un nuevo producto
PUT Amarillo Actualizar (completo) Si No Reemplazar un producto existente
PATCH Morado Actualizar (parcial) No No Actualizar solo el precio de un producto
DELETE Rojo Eliminar Si No Eliminar un producto

Idempotencia

Un metodo es idempotente cuando multiples solicitudes identicas producen el mismo efecto que una sola solicitud. GET, PUT y DELETE son idempotentes. POST no lo es, ya que cada solicitud puede crear un recurso diferente.

Seguridad

Un metodo es seguro cuando no modifica el estado del servidor. GET y HEAD son seguros. POST, PUT, PATCH y DELETE no lo son porque modifican datos en el servidor.

Convencion de Nombrado de Endpoints:
  • Usar sustantivos en plural: /productos, /usuarios, /pedidos
  • Evitar verbos en la URL: ❌ /api/crearProducto, ✅ /api/productos
  • Anidar recursos cuando sea logico: /usuarios/1/pedidos
  • Usar parametros de ruta para identificadores: /productos/123
  • Usar query params para filtros: /productos?categoria=electronica
Ejemplo de Verbos HTTP en Accion JavaScript 
// GET - Obtener todos los productos
app.get('/api/productos', (req, res) => {
  // Retorna lista de productos
});

// GET - Obtener un producto especifico
app.get('/api/productos/:id', (req, res) => {
  // Retorna un producto por ID
});

// POST - Crear un nuevo producto
app.post('/api/productos', (req, res) => {
  // Crea un nuevo producto con los datos del body
});

// PUT - Actualizar producto completo
app.put('/api/productos/:id', (req, res) => {
  // Reemplaza completamente el producto con ID :id
});

// PATCH - Actualizar producto parcialmente
app.patch('/api/productos/:id', (req, res) => {
  // Actualiza solo los campos enviados en el body
});

// DELETE - Eliminar un producto
app.delete('/api/productos/:id', (req, res) => {
  // Elimina el producto con ID :id
});

Clasificacion de Endpoints segun su Funcionalidad

En el ecosistema de Express, los endpoints se categorizan segun el verbo HTTP que implementan, cada uno con un proposito especifico en el diseno de APIs RESTful:

GET - Consulta de Datos

Utilizado para recuperar informacion del servidor sin modificar el estado del recurso. Es idempotente y seguro, lo que significa que multiples solicitudes identicas producen el mismo resultado.

POST - Creacion de Recursos

Empleado para enviar datos al servidor y crear nuevos recursos. No es idempotente, ya que cada solicitud puede generar un recurso diferente o efectos secundarios en el sistema.

PUT - Actualizacion Completa

Reemplaza completamente un recurso existente con los datos proporcionados. Requiere que el cliente envie la representacion completa del recurso.

DELETE - Eliminacion

Remueve un recurso especifico del servidor. Generalmente requiere autenticacion y autorizacion para prevenir eliminaciones accidentales.

PATCH - Actualizacion Parcial

Modifica parcialmente un recurso existente. A diferencia de PUT, solo requiere los campos que se desean actualizar, lo que lo hace mas eficiente para cambios incrementales.

HEAD - Metadatos

Identico a GET pero sin el cuerpo de la respuesta. Util para verificar la existencia de un recurso o obtener sus metadatos sin transferir datos pesados.

i
Nota Academica: La eleccion del verbo HTTP adecuado es fundamental para diseñar APIs que sigan los principios RESTful y sean intuitivas para los desarrolladores que consumen nuestros servicios.

Endpoints para Gestion de Archivos y Directorios

Express proporciona mecanismos especializados para manejar la transferencia de archivos, tanto para subida (upload) como para descarga (download) y acceso a directorios estaticos.

Acceso a Directorios Estaticos

Mediante el middleware express.static, Express puede servir archivos estaticos como imagenes, hojas de estilo y JavaScript desde un directorio especifico.

Servir Archivos Estaticos 
app.use('/static', express.static('public'));

Subida de Archivos (Upload)

Para recibir archivos desde el cliente, se utiliza middleware como multer o formidable que procesan formularios multipart/form-data y exponen los archivos en req.file.

Subida con Multer 
const multer = require('multer');
const upload = multer({ dest: 'uploads/' });

app.post('/upload', upload.single('file'), (req, res) => {
  // req.file contiene los metadatos del archivo
  res.json({ message: 'Archivo subido correctamente', file: req.file });
});

Descarga de Archivos

Express facilita la descarga de archivos mediante el metodo res.download(), que establece las cabeceras adecuadas para que el navegador inicie la descarga.

Descarga de Archivos 
app.get('/download/:filename', (req, res) => {
  const filePath = `./uploads/${req.params.filename}`;
  res.download(filePath, (err) => {
    if (err) res.status(404).json({ error: 'Archivo no encontrado' });
  });
});
Consideraciones sobre Archivos: Al manejar subidas de archivos, es crucial implementar validaciones de tipo, tamaño y contenido para prevenir ataques de denegacion de servicio o ejecucion de codigo malicioso. Ademas, se recomienda almacenar los archivos en servicios externos como S3 para entornos de produccion.

Ejemplos Practicos de Endpoints con Parametros

Los endpoints pueden recibir diferentes tipos de parametros para personalizar las respuestas segun las necesidades del cliente. A continuacion se presentan ejemplos de cada tipo:

Endpoint GET con Parametros de Ruta (Route Parameters)

Los parametros de ruta se definen en la URL y se acceden mediante req.params.

GET con Parametros de Ruta 
app.get('/api/usuarios/:id', (req, res) => {
  const userId = req.params.id;
  // Buscar usuario con ese ID en la base de datos
  res.json({ usuario: { id: userId, nombre: 'Juan' } });
});

Endpoint GET con Parametros de Consulta (Query Parameters)

Los parametros de consulta se envian en la URL despues del signo de interrogacion y se acceden mediante req.query. Son utiles para filtros, paginacion y ordenamiento.

GET con Query Parameters 
app.get('/api/productos', (req, res) => {
  const { categoria, precioMin, precioMax, pagina, limite } = req.query;
  // Construir query de base de datos con los filtros
  res.json({ 
    productos: [/* productos filtrados */], 
    paginacion: { pagina, limite, total: 100 } 
  });
});

Endpoint POST con Cuerpo (Request Body)

Los endpoints POST reciben datos en el cuerpo de la solicitud, que pueden ser JSON, formularios o archivos multipart. Se accede mediante req.body tras configurar el middleware correspondiente.

POST con Body JSON 
app.post('/api/usuarios', (req, res) => {
  const { nombre, email, password } = req.body;
  // Validar y crear nuevo usuario
  const nuevoUsuario = { id: 101, nombre, email };
  res.status(201).json({ usuario: nuevoUsuario });
});
Buenas Practicas: Para endpoints con muchos parametros, se recomienda usar query params para filtros y paginacion, route params para identificadores de recursos, y el body para datos complejos en operaciones de escritura. Ademas, siempre valide y sanitice los datos de entrada.

Analogia Conceptual: El Club VIP

Para facilitar la comprension de la arquitectura de autenticacion, utilizaremos la analogia de un evento privado de acceso restringido:

Analogia Control de Acceso Perimetral

JWT (Credencial Digital / Pulsera VIP)

Representa una pulsera criptografica intransferible otorgada tras autenticar tu identidad en taquilla. Contiene tus privilegios codificados y una firma de seguridad infalsificable generada por el establecimiento. Como una pulsera con codigo QR que solo el sistema del club puede verificar.

Middleware (El Personal de Seguridad)

Funciona como el filtro de seguridad apostado en los accesos VIP. Intercepta al asistente antes de su ingreso, verifica la integridad matematica de la firma en la pulsera y autoriza el paso o ejecuta la expulsion inmediata. Es la primera linea de defensa.

Endpoint Protegido (Area VIP)

Son las areas de acceso restringido dentro del evento, como la zona de artistas o la sala privada. Solo los asistentes con la pulsera validada pueden ingresar. Cada endpoint protegido es un espacio exclusivo dentro del servidor.

Flujo en la Practica: El cliente (asistente) se autentica en la taquilla (POST /login) y recibe su pulsera JWT. Luego, al intentar acceder a cualquier area VIP (endpoint protegido), el personal de seguridad (middleware) verifica la pulsera antes de permitir el ingreso. Sin la pulsera o con una firma invalida, el acceso es denegado inmediatamente.

Estructura y Especificacion de un JSON Web Token (RFC 7519)

Un JWT es un estandar abierto (RFC 7519) que define un metodo compacto y autonomo para transmitir informacion estructurada de forma segura entre partes como un objeto JSON. Se compone de 3 cadenas delimitadas por puntos (.) codificadas en Base64URL:

Header Encabezado

Especifica el tipo de token y el algoritmo de firma hash utilizado para la autenticacion.

{"alg": "HS256", "typ": "JWT"}

Payload Carga Util

Contiene los claims (declaraciones de la entidad y metadatos del token). Incluye informacion como el ID del usuario, su rol y el tiempo de expiracion.

{"sub": 101, "role": "docente", "iat": 17000000, "exp": 17000360}

Signature Firma Criptografica

Valida que el mensaje no haya sido alterado en el transito y confirma la identidad del emisor. Se genera combinando las dos primeras partes con una clave secreta.

HMACSHA256(Base64(H) + "." + Base64(P), Secret)
i
Principio de Seguridad Criptografica: El Payload solo esta codificado en Base64, no encriptado. Cualquier entidad intermedia puede leer su contenido. Por estandar, nunca se deben almacenar datos confidenciales (como contraseñas o tokens de sesion de terceros) en esta seccion. La confidencialidad se logra mediante el uso de JWE (JSON Web Encryption), que encripta el contenido completo.

El Patron Middleware en Express.js

Un Middleware es un bloque funcional que se ejecuta de manera secuencial dentro del ciclo de solicitud-respuesta (Request-Response Cycle) en Express. Tiene acceso completo al objeto de solicitud (req), al objeto de respuesta (res) y a la siguiente funcion de middleware mediante la funcion next().

  • ✓ req (Request Object): Instancia encargada de encapsular el flujo de entrada HTTP. Permite la inyeccion de contexto personalizado (ej: req.user = decodedData) que se propaga a traves de toda la cadena de middlewares.
  • ✓ res (Response Object): Instancia que gestiona la comunicacion de salida. Permite la finalizacion prematura del ciclo mediante respuestas de estado (ej: 401 Unauthenticated o 403 Forbidden).
  • ✓ next() (Pivote de Control): Funcion callback que, al ser invocada, cede el control de la ejecucion al siguiente middleware en la pila (middleware stack). Si no se invoca, la peticion queda colgada sin respuesta.
Estructura de un Middleware JavaScript 
function miMiddleware(req, res, next) {
  // Logica de procesamiento
  console.log('Middleware ejecutado');
  
  // Pasar el control al siguiente middleware
  next();
}

// Uso en un endpoint
app.get('/ruta', miMiddleware, (req, res) => {
  res.json({ message: 'Endpoint protegido' });
});

Flujo Completo de Autenticacion Stateless

Fase 1: Autenticacion Inicial — El Cliente emite credenciales validas mediante POST /api/v1/login con email y password.
▼
Fase 2: Generacion de Token — El Servidor valida las credenciales contra la base de datos, firma un JWT con una clave privada y lo retorna al Cliente en la carga de respuesta. El token incluye informacion del usuario y un tiempo de expiracion.
▼
Fase 3: Solicitud de Recurso Protegido — El Cliente consulta un Endpoint restringido enviando el encabezado estandar: Authorization: Bearer <TOKEN>. Este es el mecanismo estandarizado para transmitir credenciales en APIs.
▼
Fase 4: Intercepcion y Verificacion — El Middleware de Autenticacion intercepta la solicitud, deserializa la firma y ejecuta next() si el token es valido o retorna un error HTTP 401 (no autenticado) o 403 (prohibido) si ha sido alterado o expirado. Si todo es correcto, la informacion del usuario se inyecta en req.user para uso posterior.
Ventaja del Modelo Stateless: Al no requerir almacenamiento de sesion en el servidor, esta arquitectura escala horizontalmente de forma natural. Cualquier instancia del servidor puede verificar el token de forma independiente, lo que permite balanceo de carga sin configuraciones adicionales. Esto es posible gracias al principio Stateless de REST que vimos anteriormente.

const jwt = require('jsonwebtoken');
require('dotenv').config();

function authenticateToken(req, res, next) {
  const authHeader = req.headers['authorization'];
  const token = authHeader && authHeader.split(' ')[1];

  if (!token) {
    return res.status(401).json({
      status: 'error',
      error: 'Acceso no autorizado. Token no suministrado.'
    });
  }

  try {
    const decoded = jwt.verify(token, process.env.JWT_SECRET);
    req.user = decoded;
    next();
  } catch (err) {
    return res.status(403).json({
      status: 'error',
      error: 'Token invalido o expirado.'
    });
  }
}

Ejemplo de Abstraccion para el Frontend JavaScript 
// Funcion helper para todas las peticiones a la API
async function apiRequest(endpoint, options = {}) {
  const token = localStorage.getItem('token');
  
  const defaultOptions = {
    headers: {
      'Content-Type': 'application/json',
      ...(token && { 'Authorization': `Bearer ${token}` })
    }
  };

  const response = await fetch(`http://localhost:3000/api/v1${endpoint}`, {
    ...defaultOptions,
    ...options,
    headers: { ...defaultOptions.headers, ...options.headers }
  });

  if (response.status === 401) {
    // Token expirado - redirigir a login
    localStorage.removeItem('token');
    localStorage.removeItem('user');
    window.location.href = '/login';
    throw new Error('Sesion expirada');
  }

  if (!response.ok) {
    const error = await response.json();
    throw new Error(error.error || `HTTP error! status: ${response.status}`);
  }

  return await response.json();
}

Consideraciones Tecnicas y Argumentacion Academica

  • ▪
    Escalabilidad Stateless (Sin Estado): A diferencia de las sesiones basadas en Cookies y Redis/Memcached, las arquitecturas basadas en JWT no requieren que el servidor persista estados de sesion en memoria centralizada, lo que facilita el escalado horizontal tras un balanceador de carga. Cada instancia del servidor puede validar tokens de forma independiente. Este es el principio Stateless de REST aplicado en la practica.
  • ▪
    Seguridad de Contraseñas: Se utiliza bcrypt para hashear las contraseñas antes de almacenarlas en la base de datos. Esto garantiza que incluso si la base de datos es comprometida, las contraseñas originales no pueden ser recuperadas facilmente.
  • ▪
    Inyeccion SQL: Se utilizan consultas preparadas (prepared statements) con mysql2/promise para prevenir ataques de inyeccion SQL. Los parametros se pasan como un array separado de la consulta SQL.
  • ▪
    Validacion de Archivos: La configuracion de Multer incluye validacion de tipo MIME y tamaño para evitar que los usuarios suban archivos maliciosos o demasiado grandes.
  • ▪
    Estandar de Encabezados (Authorization Header): El uso del prefijo Bearer indica que la entidad solicitante es la portadora legitima del token de autorizacion otorgado previamente. Este formato esta estandarizado en RFC 6750.
  • ▪
    Codificacion Base64URL vs Encriptacion: La codificacion Base64URL no proporciona confidencialidad, sino formateo para transmision sobre HTTP. La proteccion contra alteracion de datos descansa enteramente en la Signature (Firma Simetrica/Asimetrica).
  • ▪
    Gestion del Ciclo de Vida del Token: La propiedad expiresIn configurada en 1h limita la validez del token. Para sesiones largas, se recomienda implementar un sistema de refresh tokens que permita renovar el token sin necesidad de reautenticar.
  • ▪
    CORS (Cross-Origin Resource Sharing): Para entornos de desarrollo con frontend y backend separados, configure CORS en el servidor Express usando el middleware cors: npm install cors y luego app.use(cors()).
  • ▪
    Variables de Entorno: Utilice dotenv para manejar configuraciones sensibles como la clave secreta JWT y las credenciales de la base de datos. Nunca suba el archivo .env al repositorio de control de versiones.
