Fundamentos Teóricos: Transacciones, ACID y Símbolo @

¿Qué es una Transacción?

Es un conjunto de una o varias operaciones SQL (INSERT, UPDATE, DELETE) que se ejecutan como una sola unidad indivisible de trabajo. O se ejecutan todas con éxito, o no se ejecuta ninguna (volviendo al estado original).

Propiedades ACID de la Base de Datos:
  • A - Atomicidad (Atomic): Principio de "todo o nada". Si una sola consulta dentro del bloque falla, se revierte toda la operación.
  • C - Consistencia (Consistency): La base de datos pasa de un estado válido a otro estado válido, respetando todas las reglas e integridades.
  • I - Aislamiento (Isolation): Transacciones concurrentes no interfieren entre sí. Los datos intermedios no se ven hasta confirmar.
  • D - Durabilidad (Durability): Una vez confirmada la transacción (COMMIT), los cambios se guardan permanentemente en disco.
Uso del símbolo @ en MariaDB / MySQL:

El símbolo @ antepuesto a una palabra identifica una Variable de Sesión de Usuario (ej. @pedido_id).

  • Variables Locales (sin @): Se declaran con DECLARE y solo existen dentro de un bloque BEGIN ... END de un procedimiento o función.
  • Variables de Sesión (con @): Viven durante toda la conexión del usuario. Se usan para capturar valores generados (como LAST_INSERT_ID()) o para leer parámetros de salida (OUT) en procedimientos almacenados desde la consola o desde Node.js.

Acotación Técnica Importante: Delimitadores en MariaDB

Al crear objetos guardados como Triggers, Funciones o Procedimientos Almacenados, el motor de la base de datos necesita procesar múltiples sentencias terminadas en punto y coma (;) como un solo bloque.

Uso del DELIMITER según el cliente de BD:
  • Línea de comandos / phpMyAdmin: Es obligatorio redefinir el delimitador usando DELIMITER // antes del bloque de código y restaurarlo con DELIMITER ; al final.
  • DBeaver / MySQL Workbench / HeidiSQL: Estos clientes gestionan la delimitación automáticamente cuando seleccionas el bloque completo o usas la interfaz visual. Si ejecutas como script completo, la directiva DELIMITER // también es compatible.
-- Ejemplo de sintaxis con cambio de delimitador
DELIMITER //

CREATE PROCEDURE sp_ejemplo()
BEGIN
    -- Múltiples sentencias terminadas en ;
    SELECT * FROM productos;
END //

DELIMITER ;
Explicación del bloque: DELIMITER // le dice al cliente que reemplace el caracter final del comando (que usualmente es ;) por //. Esto evita que el motor se detenga al leer el primer ; dentro del bloque de código. Al finalizar con END //, restauramos con DELIMITER ;.

Ejemplo 1: Transacciones y Triggers (Integridad de Datos)

Garantía de operaciones atómicas ACID y automatización de auditorías en el motor de base de datos sin sobrecargar la aplicación Node.js.

1. Tabla para historial de auditoría

CREATE TABLE historial_precios (
    id INT AUTO_INCREMENT PRIMARY KEY,
    producto_id INT NOT NULL,
    precio_anterior DECIMAL(10, 2) NOT NULL,
    precio_nuevo DECIMAL(10, 2) NOT NULL,
    fecha_registro DATETIME DEFAULT CURRENT_TIMESTAMP
);
Explicación: Creamos una tabla desacoplada que servirá de bitácora para guardar automáticamente un registro cada vez que el precio de un producto sea modificado.

2. Creación del Trigger de Auditoría

DELIMITER //

CREATE TRIGGER trg_auditoria_precio_producto
AFTER UPDATE ON productos
FOR EACH ROW
BEGIN
    IF OLD.precio <> NEW.precio THEN
        INSERT INTO historial_precios (producto_id, precio_anterior, precio_nuevo)
        VALUES (OLD.id, OLD.precio, NEW.precio);
    END IF;
END //

DELIMITER ;
Explicación detallada:
  • AFTER UPDATE ON productos FOR EACH ROW: Indica que el código se disparará automáticamente inmediatamente después de actualizar cada fila de la tabla productos.
  • OLD y NEW: Son estructuras especiales. OLD.precio es el precio antes de la actualización; NEW.precio es el nuevo valor.
  • IF OLD.precio <> NEW.precio THEN: Evalúa si el precio realmente cambió antes de insertar en la bitácora, evitando registros innecesarios si solo se actualizó otro campo (como el nombre).

3. Control Manual de Transacción en MariaDB / MySQL

START TRANSACTION;

INSERT INTO pedidos (cliente_id, fecha, total) VALUES (1, NOW(), 150.00);
SET @pedido_id = LAST_INSERT_ID();

INSERT INTO detalles_pedido (pedido_id, producto_id, cantidad, precio) VALUES (@pedido_id, 5, 2, 75.00);
UPDATE productos SET stock = stock - 2 WHERE id = 5;

-- Si todo es correcto y no hay fallas:
COMMIT;

-- En caso de error en algún paso intermedio:
-- ROLLBACK;
Explicación detallada:
  • START TRANSACTION;: Inicia la unidad indivisible de trabajo y deshabilita la confirmación automática (autocommit).
  • SET @pedido_id = LAST_INSERT_ID();: Guarda en la variable de sesión @pedido_id el ID autogenerado del pedido recién insertado para usarlo en la siguiente fila de detalle.
  • COMMIT;: Aplica todos los cambios permanentemente en disco si todas las sentencias fueron exitosas. Si alguna fallara, se debe ejecutar ROLLBACK; para revertir todo al estado inicial.

Ejemplo 2: Vistas y Stored Functions (Abstracción y Optimización)

Simplificación de consultas repetitivas complejas (JOINs) y encapsulamiento de cálculos en el servidor de base de datos.

1. Creación de una Vista (`VIEW`)

CREATE VIEW v_resumen_pedidos AS
SELECT 
    p.id AS pedido_id,
    c.nombre AS cliente,
    c.email AS email_cliente,
    p.total,
    p.fecha
FROM pedidos p
INNER JOIN clientes c ON p.cliente_id = c.id;

-- Consulta desde la aplicación:
SELECT * FROM v_resumen_pedidos WHERE total > 100.00;
Explicación: La vista actúa como una tabla virtual. Oculta la complejidad de hacer JOINs repetitivos. Desde la aplicación Node.js solo se invoca con un simple SELECT.

2. Creación de una Stored Function

DELIMITER //

CREATE FUNCTION fn_calcular_iva(monto DECIMAL(10,2), porcentaje DECIMAL(4,2))
RETURNS DECIMAL(10,2)
DETERMINISTIC
BEGIN
    RETURN monto * (porcentaje / 100);
END //

DELIMITER ;

-- Uso en consultas SQL:
SELECT id, total, fn_calcular_iva(total, 16.00) AS iva FROM pedidos;
Explicación detallada:
  • RETURNS DECIMAL(10,2): Declara qué tipo de dato devolverá la función.
  • DETERMINISTIC: Le comunica al motor que para las mismas entradas, la función siempre retornará la misma salida. Esto optimiza la memoria caché.
  • RETURN ...: Realiza el cálculo matemático y retorna el valor directamente en la consulta.

Ejemplo 3: Stored Procedures (Procedimientos Almacenados)

Encapsulamiento de lógica de negocio completa dentro de MariaDB con control de flujo y manejo de excepciones.

DELIMITER //

CREATE PROCEDURE sp_registrar_compra(
    IN p_cliente_id INT,
    IN p_producto_id INT,
    IN p_cantidad INT,
    OUT p_resultado VARCHAR(100)
)
BEGIN
    DECLARE v_stock_actual INT;
    DECLARE v_precio DECIMAL(10,2);
    
    -- Manejo de excepciones (Manejador de Errores SQL)
    DECLARE EXIT HANDLER FOR SQLEXCEPTION
    BEGIN
        ROLLBACK;
        SET p_resultado = 'ERROR: Transacción abortada por fallo en el sistema.';
    END;

    START TRANSACTION;

    SELECT stock, precio INTO v_stock_actual, v_precio 
    FROM productos WHERE id = p_producto_id;

    IF v_stock_actual >= p_cantidad THEN
        UPDATE productos SET stock = stock - p_cantidad WHERE id = p_producto_id;
        
        INSERT INTO pedidos (cliente_id, fecha, total) 
        VALUES (p_cliente_id, NOW(), v_precio * p_cantidad);
        
        COMMIT;
        SET p_resultado = 'ÉXITO: Compra registrada correctamente.';
    ELSE
        ROLLBACK;
        SET p_resultado = 'RECHAZADO: Stock insuficiente.';
    END IF;
END //

DELIMITER ;
Explicación detallada:
  • IN / OUT: Parámetros de entrada (IN) que vienen desde Node.js y parámetros de salida (OUT) para devolver datos/mensajes.
  • DECLARE v_stock_actual INT;: Declaración de variables locales privadas (sin @), válidas solo dentro del bloque BEGIN ... END.
  • DECLARE EXIT HANDLER FOR SQLEXCEPTION: Equivalente a un bloque catch. Si ocurre un fallo inesperado de SQL, ejecuta ROLLBACK inmediatamente y le asigna el error a p_resultado.
  • SELECT stock, precio INTO ...: Consulta la base de datos y asigna los valores a las variables locales.
  • IF ... ELSE: Estructura condicional para tomar decisiones: si hay stock, descuenta inventario, inserta el pedido, hace COMMIT y retorna éxito; si no, hace ROLLBACK y rechaza.

Ejemplo 4: Integración API REST en Express (Patrón MVC)

Consumo de Objetos Avanzados de MariaDB/MySQL mediante funciones exported dentro del Modelo y Controlador de Express con el paquete mysql2/promise.

1. Modelo de Datos (`models/pedidoModel.js`)

const db = require('../config/db');

// Función exportada para consultar la vista
const obtenerResumenPedidos = async () => {
  const [rows] = await db.query('SELECT * FROM v_resumen_pedidos');
  return rows;
};

// Función exportada para ejecutar el procedimiento almacenado
const registrarCompraSP = async (clienteId, productoId, cantidad) => {
  const [rows] = await db.query(
    'CALL sp_registrar_compra(?, ?, ?, @resultado); SELECT @resultado AS resultado;',
    [clienteId, productoId, cantidad]
  );
  // MariaDB devuelve arreglos múltiples. rows[1][0].resultado extrae la respuesta de @resultado
  return rows[1][0].resultado;
};

module.exports = {
  obtenerResumenPedidos,
  registrarCompraSP
};
Explicación del Modelo:
  • obtenerResumenPedidos: Realiza un SELECT directo sobre la Vista v_resumen_pedidos. Toda la lógica de los JOINs es procesada eficientemente por el motor MariaDB.
  • registrarCompraSP: Ejecuta el procedimiento almacenado con los marcadores de posición ? (evitando inyecciones SQL). Pasa la variable de sesión @resultado para capturar el valor de salida (OUT) y ejecuta inmediatamente el SELECT @resultado en la misma conexión.

2. Controlador API REST (`controllers/pedidoController.js`)

const pedidoModel = require('../models/pedidoModel');

// GET /api/pedidos/resumen
const getResumen = async (req, res) => {
  try {
    const pedidos = await pedidoModel.obtenerResumenPedidos();
    res.status(200).json({
      status: 'success',
      data: pedidos
    });
  } catch (error) {
    res.status(500).json({
      status: 'error',
      message: 'Error al consultar el resumen de pedidos: ' + error.message
    });
  }
};

// POST /api/pedidos/comprar
const crearPedido = async (req, res) => {
  const { clienteId, productoId, cantidad } = req.body;

  if (!clienteId || !productoId || !cantidad) {
    return res.status(400).json({
      status: 'fail',
      message: 'Faltan campos obligatorios en el cuerpo de la petición.'
    });
  }

  try {
    const resultado = await pedidoModel.registrarCompraSP(clienteId, productoId, cantidad);
    
    // Si el procedimiento devolvió un rechazo por stock
    if (resultado.startsWith('RECHAZADO')) {
      return res.status(400).json({ status: 'fail', message: resultado });
    }

    res.status(201).json({
      status: 'success',
      message: resultado
    });
  } catch (error) {
    res.status(500).json({
      status: 'error',
      message: 'Error interno al procesar la compra: ' + error.message
    });
  }
};

module.exports = {
  getResumen,
  crearPedido
};

3. Definición de Rutas (`routes/pedidoRoutes.js`)

const express = require('express');
const router = express.Router();
const pedidoController = require('../controllers/pedidoController');

// Endpoint GET para obtener el resumen mediante la Vista
router.get('/resumen', pedidoController.getResumen);

// Endpoint POST para procesar una compra mediante el Stored Procedure
router.post('/comprar', pedidoController.crearPedido);

module.exports = router;
Explicación del Controlador y Rutas:
  • Mantiene la arquitectura MVC pura basada en funciones, sin clases sintácticas.
  • El Controlador valida los datos de entrada (`req.body`), invoca la función del Modelo y responde con códigos HTTP estándar (`200 OK`, `201 Created`, `400 Bad Request`, `500 Internal Server Error`).
  • El archivo de rutas mapea cada verbo HTTP (`GET`, `POST`) al método del controlador correspondiente.
